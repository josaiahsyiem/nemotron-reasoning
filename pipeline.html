P1

Per-type solvers

Six puzzle types, six implementations of the interface. This is where accuracy is actually won — and where your original contribution lives.

1.1

Easy solvers — numeral, unit, gravitational

Prove the interface on the high-pass-rate types first. verify() = numeric tolerance (±0.5% rel) or exact-string match. Fast wins that validate the ABC before the hard work.

numeral.py · unit_conversion.py · grav_constant.py
free
1.2

Text-encryption solver — cipher dictionary

Monoalphabetic substitution over a fixed vocabulary. augment_prompt() embeds the known word→cipher mapping so the model isn't guessing letters blind. Reimplemented from the idea, your code.

src/vcd/solvers/text_encryption.py
free
1.3

Bit-manipulation solver — per-bit boolean analysis

Each output bit is a boolean function of 1–3 input bits. augment_prompt() enumerates candidate functions per bit and flags CERTAIN vs AMBIGUOUS. The hard type — expect a low pass rate, keep every correct trace.

src/vcd/solvers/bit_manipulation.py
free
1.4

Equation-transformation solver

The worst-performing type in the whole competition (~13.6% pass) that no public notebook ever built a solver for. Parse the transformation rule, apply it symbolically, verify. This is the block that makes the project yours.

src/vcd/solvers/equation_transform.py

P2

Verified-CoT distillation

The core loop: generate reasoning, throw away anything that gets the answer wrong. Quality over quantity — this is the whole thesis.

2.1

Generate CoT traces

Run each solver-augmented prompt through an LLM at temperature ≈ 0.7 to produce reasoning. This is the one data-prep step that needs an LLM — an API key or a single GPU pass, your choice.

src/vcd/generate/cot_generate.py
llm
2.2

Verify + filter

Extract the answer from \boxed{}, route it to the matching solver.verify(), and keep only correct traces. This rejection-sampling step is what turns noisy generation into clean training data.

src/vcd/verify/filter.py
free
2.3

Token-budget compression

Any trace over the token budget (~7,600, leaving room for the </think>\boxed{} suffix) gets re-sent to the LLM to shorten by the overflow %, preserving the answer. Fits the reasoning inside the model's window.

src/vcd/generate/compress.py
llm
P3

Train the LoRA

The only phase that truly needs the big GPU. Everything upstream is tested before you spend a rupee of paid compute.

3.1

Blackwell / Triton env fixes

Isolated, documented plumbing: pure-PyTorch RMSNorm to dodge the broken Triton kernel, relocate ptxas-blackwell to a writable path, force the model's slow path. Understanding why each hack exists is itself an interview flex.

src/vcd/train/env_fixes.py
gpu
3.2

Build SFT dataset

Turn verified traces into chat records: user = prompt + boxed-answer suffix, assistant = CoT + </think>\boxed{answer}. Strip stray boxed tags from the body, re-append the canonical one. Loss masked to assistant tokens.

src/vcd/train/dataset.py
gpu
3.3

LoRA fine-tune

PEFT + TRL SFTTrainer. Rank 32 / alpha 32, target the projection modules, bf16, gradient checkpointing, cosine schedule, 1–2 epochs. Run 2–3 rank configs so you have an ablation, not a single number.

src/vcd/train/train_lora.py
gpu
P4

Serve, benchmark, ship

The layer none of the three notebooks have — and exactly the production evidence your resume was missing.

4.1

SVD rank-compression (optional)

If a merge pushes fused-projection LoRA ranks over 32, reconstruct Δ = B·A, SVD, truncate to rank 32, redistribute √S. Include it as a standalone module — it's a clean proof you understand LoRA math.

src/vcd/merge/svd_compress.py
free
4.2

vLLM serve + inference benchmark

Serve the merged model on vLLM; sweep concurrency 1→64 and record TTFT, p50/p95 latency, tokens/sec, and peak VRAM. This table is your headline MLOps result — no competitor notebook measures serving.

src/vcd/infer/vllm_serve.py · infer/benchmark.py
gpu
